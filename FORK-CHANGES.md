# bandzalkin/band-sdk-python fork changes

Commit-pinned fork of [band-ai/band-sdk-python](https://github.com/band-ai/band-sdk-python)
consumed by [band-ai/band-agent](https://github.com/band-ai/band-agent) as its `band-sdk`
dependency. It carries upstream pull requests that band-agent needs before upstream
merges and releases them, so band-agent never monkeypatches the SDK.

## The rule

band-agent's SDK is upstream `main` plus our open upstream pull requests at their
current heads, plus this fork's own files (this file, `.github/band-agent/` and the
replay workflow). Nothing else.

- A pull request that conflicts with a newer upstream `main` is rebased **in its
  upstream pull request**, never resolved in the fork.
- A fix found while using the SDK goes into the pull request it belongs to.
- Two of our pull requests must apply on top of each other; if they touch the same
  lines, one of them is changed upstream so they do not.

## How it is built

`.github/band-agent/prs.txt` lists the pull requests, in the order they are applied.
`N after M` marks N as stacked on M: while M is open, only N's own changes on top of
M's head are applied.

Shared shutdown repair #909 and the native OMP transport and adapter (#897 and
#898) are part of upstream `main`. The selected runtime scheduler #816 preserves
recovery past exhausted failed messages; activity-name gating #901 is stacked
on it. The remaining native OMP stack starts at #899, with each subsequent
layer listing its immediate predecessor with `after`.

The [manifest](.github/band-agent/prs.txt) is the source of truth for the selected
pull requests and their ordering.

Identical shared, Windows Job and ACP cleanup corrections carried by multiple
selected pull requests must compose once in the resulting tree. Any disagreement
is corrected in the owning upstream pull request, not with a fork patch.

Every day at 06:17 UTC (or on a manual dispatch) `.github/workflows/band-agent-replay.yml`
runs `.github/band-agent/replay.py`, which:

1. Starts from current upstream `main` and applies this fork's own commits.
2. Reads each listed pull request from GitHub and applies its current head's own
   changes as one commit (trailers `Source-Base`, `Source-Head`, `Upstream-PR`).
   - Merged or closed: skipped, and the run summary asks to remove it from the list.
   - Stacked on a prerequisite that is no longer open: its changes since `main` are
     applied, with a note.
   - Does not apply, or a stacked pull request is not built on its prerequisite's
     current head: the run fails and names the pull request to rebase upstream.
3. If the result differs from the last staged revision, runs locked sync, all
   pre-commit hooks and pytest, then publishes a `staged/<date>-<sha>` tag and
   updates `band-agent-patches-latest`. An unchanged result publishes nothing.

Run it locally with `python .github/band-agent/replay.py --dry-run` from a checkout of
`band-agent-patches` with remotes `origin` (this fork) and `upstream` (band-ai), and
`gh` signed in. It leaves the result checked out on `band-agent-patches-latest`.

These checks are not the whole upstream CI matrix; each pull request's own upstream CI
covers the rest.

## Branches and tags

| Ref | Content |
| --- | --- |
| `main` | Mirrors upstream `main`. Never commit here. |
| `band-agent-patches` (default) | Upstream `main` plus this fork's own commits; no pull request copies. |
| `band-agent-patches-latest` | Generated by the replay. Never commit here. |
| `staged/<date>-<sha>` tags | Revisions that passed the replay's checks. |

band-agent pins a staged revision by its full commit SHA in `pyproject.toml` and
`uv.lock`; it never follows a branch. The generated branch is force-updated, so its
`staged/` tag keeps an existing pin fetchable.

## Changing the pull requests

- **Add one:** append it to `prs.txt` (with `after M` if it is stacked) and push to
  `band-agent-patches`; the next replay applies it.
- **Merged or closed:** remove it from `prs.txt` when the run summary says so.
- **A run failed on a conflict:** rebase the named pull request upstream onto current
  `main`; the next run picks up the new head.

band-agent's SDK fork watch then opens the pin pull request for the new staged
revision, which merges once its CI passes and it is approved.
