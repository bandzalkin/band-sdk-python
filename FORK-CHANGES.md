# bandzalkin/band-sdk-python fork changes

Commit-pinned fork of [band-ai/band-sdk-python](https://github.com/band-ai/band-sdk-python)
consumed by [band-ai/band-agent](https://github.com/band-ai/band-agent) as its `band-sdk`
dependency. It carries upstream pull requests that band-agent needs before upstream
merges and releases them, so band-agent never monkeypatches the SDK.

## The rule

The fork is upstream `main` plus our open upstream pull requests, each copied
exactly as its current head, plus this file and the replay workflow. Nothing else.

- A pull request that conflicts with a newer upstream `main` is rebased **in its
  upstream pull request**, never resolved in the fork.
- A fix found while using the fork goes into the pull request it belongs to.
- When a pull request changes upstream (new commits, a rebase, review fixes), its
  squash here is replaced by the new head.
- Two of our pull requests must apply on top of each other without conflicts; if
  they touch the same lines, one of them is changed upstream so they do not.
- A merged pull request is dropped; a closed one is dropped.

## Branches and tags

| Ref | Content |
| --- | --- |
| `main` | Mirrors upstream `main`. Never commit here. |
| `band-agent-patches` (default) | Upstream `main`, the fork commit, then one squash per pull request, as a linear history. |
| `band-agent-patches-latest` | Generated by replay onto the newest upstream `main`. Never commit here. |
| `staged/<date>-<sha>` tags | Revisions that passed the replay's locked install, pre-commit and pytest gate. |

band-agent pins a staged revision by its full commit SHA in `pyproject.toml` and
`uv.lock`; it never follows a branch. The generated branch can be force-updated,
so its `staged/` tag keeps an existing pin fetchable when branch heads move.

## Weekly upstream replay

`.github/workflows/band-agent-replay.yml`:

1. Runs Mondays at 06:17 UTC, or on a manual dispatch.
2. Fetches current upstream `main` and walks the fork's commits in order.
3. Skips a squash whose pull request has merged; keeps unlabelled commits.
4. Cherry-picks onto current upstream `main`. A conflict fails the run before
   checks or publication, leaving band-agent on its existing pin; the fix is a
   rebase of the conflicting pull request upstream.
5. For a changed tree, runs locked sync, all pre-commit hooks and pytest, then
   publishes a `staged/` tag and updates the generated branch.

These checks are not the whole upstream CI matrix; each pull request's own
upstream CI covers the rest.

The band-agent freshness workflow files an issue when the replay is not green
or a newer staged revision exists.

## Updating the patch set

1. Fetch upstream `main` and each pull request head.
2. In an isolated worktree from upstream `main`: commit the fork commit, then
   cherry-pick each pull request's own commits squashed into one commit, in the
   order above, with the trailers.
3. Run `uv sync --all-packages --locked --extra dev`, `pre-commit run --all-files`
   and `pytest -q`.
4. Update this table, publish to `band-agent-patches` with an explicit
   expected-head `--force-with-lease`, and dispatch the replay.
5. To move band-agent, pin the staged SHA, run
   `uv lock --upgrade-package band-sdk`, and run band-agent's full gate.
