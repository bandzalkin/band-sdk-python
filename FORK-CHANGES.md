# bandzalkin/band-sdk-python fork changes

Commit-pinned fork of [band-ai/band-sdk-python](https://github.com/band-ai/band-sdk-python)
consumed by [band-ai/band-agent](https://github.com/band-ai/band-agent) as its `band-sdk`
dependency. It carries upstream pull requests that band-agent needs before upstream
merges and releases them, so band-agent never monkeypatches the SDK.

## Branches and tags

| Ref | Content |
| --- | --- |
| `main` | Mirrors upstream `main`. Never commit here. |
| `band-agent-patches` (default) | Upstream `main` plus the fork-only commits below, kept as a linear history. |
| `band-agent-patches-latest` | Generated by replay onto the newest upstream `main`. Never commit here. |
| `staged/<date>-<sha>` tags | Revisions that passed the replay's locked install, pre-commit and pytest gate. |

band-agent pins a staged revision by its full commit SHA in `pyproject.toml` and
`uv.lock`; it never follows a branch. The generated branch can be force-updated,
so its `staged/` tag keeps an existing pin fetchable when branch heads move.

## Weekly upstream replay

`.github/workflows/band-agent-replay.yml` retains the existing replay behavior:

1. Run Mondays at 06:17 UTC or by an explicitly authorized manual dispatch.
2. Fetch current upstream `main` and traverse fork-only commits in order.
3. Skip numeric PR trailers confirmed merged upstream. Keep closed-unmerged
   trailers and unlabelled commits; a closed PR is not proof of supersession.
4. Cherry-pick onto current upstream. An application failure exits before checks
   or publication, leaving band-agent on its existing pin.
5. Only for a changed tree, run locked dev/workspace sync, all pre-commit hooks
   and pytest; then publish a `staged/` tag and update the generated branch.
6. A tree-identical replay publishes nothing. The summary lists merged skips
   and closed-unmerged patches that were still applied.

These checks are **not the entire upstream CI matrix**. Current CI also checks
root and starter locks, baseline collection, Markdown examples, isolated wheels,
and separate dependency environments and platforms. The integration owner runs
those applicable gates separately on the assembled/staged revision.

Fork operators keep upstream release, publishing and E2E workflows disabled in
repository settings. Restoring a workflow file locally does not enable or
execute it. The band-agent freshness workflow watches replay and the SDK pin;
this foundation does not change band-agent or repository settings.

## Maintaining the linear patch set

Prepare a replacement in an isolated worktree from an exact upstream SHA. Keep
one feature squash per upstream PR, omit `CHANGELOG.md`, record source heads and
conflict resolutions, and keep prerequisite squashes separate from features.
Refresh a patch at its existing position; do not carry accepted branch merge
history or duplicate superseded no-spin machinery.

Before dropping a closed-unmerged patch, map every behavior/test hunk and execute
its replacement proof. Preserve the original source as a comparison artifact
until that proof is accepted. A maintainer's supersession statement alone does
not establish coverage. Remove a merged patch's table row when its fork squash
is removed; the replay already skips its merged trailer.

After independent review and owner authorization, publish the replacement to
`band-agent-patches` with an explicit expected-head `--force-with-lease`, dispatch
the replay, and record its upstream target, staged SHA, tag and checks. No push,
dispatch, tag, PR, merge or deployment is part of local foundation preparation.

To update band-agent later, pin the verified staged SHA, run
`uv lock --upgrade-package band-sdk`, and run band-agent's full gate and the
required fresh-install/native receipts. SDK foundation preparation is not that
Band integration.
